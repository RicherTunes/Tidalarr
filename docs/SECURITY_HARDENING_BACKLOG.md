# Security Hardening Backlog — tidalarr

_Generated: 2026-05-23 | Phase 1 security audit_

> **Note:** `docs/decisions/0001-hardcoded-tidal-client-credentials.md` already documents the
> rationale for all five hardcoded constants (`CLIENT_ID_PKCE`, `CLIENT_SECRET_PKCE`, `CLIENT_ID`,
> `REDIRECT_URI`, `MasterKeyBase64`). The findings below do NOT re-open that decision; they address
> all other dimensions.

| TID-001 | Auth & token storage | `PKCEStateStore.cs` calls `FileTokenStore.LoadAsync().GetAwaiter().GetResult()` (line 284) and `SaveAsync().GetAwaiter().GetResult()` (line 301, 330) inside static methods that are called from the Lidarr sync `IIndexer` interface. | TID-006 | Path & file validation | `TidalarrSettings` validator (lines 101–103, 127–129) delegates path validation to `PathValidationExtensions.IsReasonablePath`, which in turn calls `Common.Utilities.PathValidation.IsReasonablePath`. This is correct. However, the actual download path is used later when constructing per-track filenames in `TidalChunkDownloader` — it is not re-validated at download time. A settings value that was valid at save time but was later modified on disk could contain traversal characters if the config file is edited manually. | Medium | `src/Tidalarr/Integration/TidalarrSettings.cs:101-129` | Re-validate `DownloadPath` at download initiation (in `TidalDownloadClient` or orchestrator) by checking that the resolved path is a child of the configured root. | TID-006 |
| TID-007 | Network failure behaviour | `TidalChunkDownloader` assembles encrypted chunks and decrypts them via `TidalStreamDecryptor`. There is no hash/integrity verification of the assembled file after decryption — the security token drives decryption correctness but a partially-received chunk that produces garbled plaintext will silently produce a corrupt audio file. | High | `src/Tidalarr/Domain/Streaming/TidalChunkDownloader.cs` | After assembly + decryption, verify file length equals the expected manifest byte count. Log a warning and mark the download as failed if lengths do not match. If Tidal provides a content hash in the manifest, validate against it. | TID-007 |
| TID-008 | Network failure behaviour | `TidalStreamDecryptor.DecryptFileStreamAsync` reads the entire cipher file into a `MemoryStream` buffer (line 50: `await stream.CopyToAsync(buffer)`). For large Hi-Res FLAC tracks (can exceed 1 GB) this causes a full in-memory buffer allocation, increasing the attack surface for OOM conditions and leaving a decrypted plaintext copy in managed memory until GC collects it. | Medium | `src/Tidalarr/Domain/Streaming/TidalStreamDecryptor.cs:48-55` | Implement a streaming CTR decryption path that processes chunks in place and writes decrypted bytes directly to the output stream without full-file buffering. | TID-008 |
| TID-009 | Rate limiting | Tidalarr has its own `TidalRateLimiter.cs` AND `TidalRateLimitingHandler.cs` alongside the Common `UniversalAdaptiveRateLimiter`. This dual-layer means Tidal API calls pass through both rate-limiters, potentially double-throttling or double-counting hits, and creating confusion about which limiter is authoritative. | Medium | `src/Tidalarr/Infrastructure/Performance/TidalRateLimiter.cs`, `TidalRateLimitingHandler.cs` | Audit whether both limiters are wired into the same `HttpClient` pipeline. If so, retire the plugin-local `TidalRateLimiter` and delegate exclusively to Common's `UniversalAdaptiveRateLimiter` under the `"Tidal"` service key. | TID-009 |
| TID-010 | Sensitive logging | `TidalHealthDiagnostics.cs` and `TidalTelemetry.cs` emit telemetry data.
